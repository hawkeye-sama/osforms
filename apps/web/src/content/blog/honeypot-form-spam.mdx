A honeypot field is a hidden input that people never fill and spam bots usually do, so any submission that arrives with it filled can be thrown away. It stops most automated form spam without a CAPTCHA, a puzzle, or any friction for real visitors. The catch is that the details matter: hide it the wrong way and bots skip it, name it the wrong way and your visitors' autofill trips it.

Every public form gets found, usually sooner than you'd think, and then the submissions start: SEO offers, crypto links, "I noticed your website..." The usual reflex is a CAPTCHA, which works, but every challenge you put in front of a human costs you some of the humans. A honeypot moves the work to the server, where it belongs. Below is markup that hides the field properly, how OSForms handles it, and a plain list of what a honeypot will not catch.

## How Bots Fill Fields (and Why a Honeypot Field Catches Them)

Most form spam is not clever. A crawler finds a `<form>`, reads every `input`, `textarea`, and `select` inside it, fills each one with something plausible (an email-looking string for anything named email, a URL for anything named website, filler text everywhere else), and POSTs to the `action` URL. It never renders the page. It doesn't know what is visible; it only knows what is in the HTML.

That is the whole trick. Add an input that exists in the HTML but not on the screen, and you have a field that only a non-human would fill.

If you run your own server, the check is a few lines:

```js
// Express, the DIY version
app.post('/contact', express.urlencoded({ extended: false }), (req, res) => {
  if (req.body.favorite_color) {
    return res.redirect(303, '/thanks/'); // pretend it worked
  }
  // ...validate, store, send the email
});
```

Notice the bot gets a success, not an error. An error teaches a spam script that something in its payload is wrong; a success teaches it nothing. The hard part was never this `if` statement. It's everything around it: the server, storage, email delivery, and rate limiting, for a form on a site that was otherwise static.

## Accessible Hidden-Field Markup

Here is the markup I'd use, and why each attribute is there:

```html
<form action="https://osforms.com/api/v1/f/abc123xyz" method="POST">
  <label for="email">Email</label>
  <input id="email" type="email" name="email" autocomplete="email" required />

  <label for="message">Message</label>
  <textarea id="message" name="message" required></textarea>

  <!-- Honeypot: off-screen, out of the tab order, hidden from screen readers -->
  <div class="hp" aria-hidden="true">
    <label for="favorite_color">Leave this field empty</label>
    <input
      id="favorite_color"
      type="text"
      name="favorite_color"
      tabindex="-1"
      autocomplete="off"
    />
  </div>

  <button type="submit">Send</button>
</form>
```

```css
.hp {
  position: absolute;
  left: -10000px;
  width: 1px;
  height: 1px;
  overflow: hidden;
}
```

**Off-screen, not `display:none`.** An `<input type="hidden">` or an inline `style="display:none"` is the easiest honeypot to detect, and some bots skip both for exactly that reason. A class in your stylesheet that moves the field off-screen leaves it looking like any other text input in the HTML.

**`aria-hidden="true"` on the wrapper** removes the field and its label from the accessibility tree, so screen reader users never hear about it.

**`tabindex="-1"`** keeps keyboard users from tabbing into it. Without this, a sighted keyboard user can land in an invisible field and type into it.

**The visible-if-broken label.** If your stylesheet fails to load, the field shows up. "Leave this field empty" tells a human what to do in that case. The trade-off is that a bot reading labels could take the hint; I'd keep it, because a broken stylesheet is more likely than a bot that parses label text.

### Pick a name autofill won't touch

This is where honeypots quietly cost people real leads. Browsers and password managers decide what to fill by matching on the field's `name`, `id`, and label. Name your honeypot `website`, `url`, `company`, or `phone` and a visitor's autofill may fill it, and the endpoint will throw away a real message without anyone noticing. `autocomplete="off"` doesn't fully save you: [MDN notes](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/autocomplete) that browsers may ignore it on login fields to support password managers (November 2026).

| Honeypot name             | Risk                                                                  |
| ------------------------- | --------------------------------------------------------------------- |
| `website`, `url`          | Autofill matches the `url` token; real visitors can trip it           |
| `email2`, `phone`, `name` | Matches contact-info heuristics in browsers and password managers     |
| `honeypot`, `_gotcha`     | Safe from autofill, but well known; targeted scripts may skip them    |
| `favorite_color`          | Plausible to a bot, matches no autofill token, unlikely to be skipped |

The best name looks like a field a form might ask for but no browser knows how to fill.

## The Honeypot Field in OSForms

The honeypot in OSForms is **off until you name it**. There's no magic field name baked in. Open your form's **Settings** dialog, enter the name under **Honeypot Field Name** (the placeholder shows `_gotcha`, but use your own, like `favorite_color`), and save. The name in the dashboard and the `name` attribute in your markup must match exactly.

Then the submission endpoint, `POST /api/v1/f/{slug}`, runs its checks in this order:

| Step | Check                                          | Result if it fails                          |
| ---- | ---------------------------------------------- | ------------------------------------------- |
| 1    | Active form with that slug                     | `404`                                       |
| 2    | Allowed Origins (if set)                       | `403 Origin not allowed`                    |
| 3    | Per-IP rate limit                              | `429` with a `Retry-After` header           |
| 4    | Monthly submission limit                       | `403`                                       |
| 5    | Body parses                                    | `400`                                       |
| 6    | **Honeypot field empty**                       | **Normal success response, nothing stored** |
| 7    | CAPTCHA token (if set)                         | `400`                                       |
| 8    | Store, then run integrations in the background | `200` JSON, or `303` to your redirect URL   |

Step 6 is the important one. When the named field arrives non-empty, the endpoint returns exactly what a real visitor gets: `{"success":true,"message":"Submission received"}`, or a `303` to your thank-you page if a redirect URL is set. Nothing is written to the database. Because the monthly counter only goes up after a submission is stored, honeypot catches **don't count toward your 100 free submissions a month**, and since no submission exists, there's no email, no Google Sheets row, and no webhook call. When the field is empty, it's stripped before storage, so it never clutters your dashboard or CSV export.

You can watch it work with two requests:

```bash
# A bot: honeypot filled. Same success response, nothing appears in the dashboard.
curl -X POST https://osforms.com/api/v1/f/abc123xyz \
  -H "Accept: application/json" \
  -d "email=bot@example.com&message=cheap+seo&favorite_color=blue"

# A person: honeypot empty. Stored, and your integrations run.
curl -X POST https://osforms.com/api/v1/f/abc123xyz \
  -H "Accept: application/json" \
  -d "email=you@example.com&message=hello&favorite_color="
```

Both print `{"success":true,"message":"Submission received"}`. Only the second shows up in the dashboard.

One gotcha if you submit with JavaScript. `new FormData(form)` picks up the honeypot automatically, which is what you want. A hand-built JSON body (`JSON.stringify({ email, message })`) leaves it out, and then the honeypot never triggers. Include the field's value in the payload, empty or not.

## What Gets Past a Honeypot Field (and When to Add reCAPTCHA)

A honeypot catches bots that fill everything. It does nothing against:

- **Scripts written for your form.** Someone who looks at your HTML once and posts only `email` and `message` sails past.
- **Browser automation.** Playwright or Puppeteer bots that render the page and type only into visible fields never touch an off-screen input.
- **People.** Paid spam is typed by hand, and a person sees what your visitors see.

Allowed Origins won't save you here either, since it's a browser check and a script can simply omit the `Origin` header. When spam starts getting through, OSForms supports **reCAPTCHA**, **hCaptcha**, and **Cloudflare Turnstile** with your own keys. Put the widget on your form (it adds a `g-recaptcha-response`, `h-captcha-response`, or `cf-turnstile-response` field) and set the matching secret on the form. The endpoint picks the verifier from that field name, so there's no provider setting to choose. The secret isn't in the Settings dialog yet; set it through the API. The quickest way is from your browser's console while signed in to the dashboard, which sends your session cookie:

```js
// Run on osforms.com while logged in. FORM_ID is the id in /dashboard/forms/FORM_ID
await fetch('/api/v1/forms/FORM_ID', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ recaptchaSecret: 'your-captcha-secret' }),
}).then((r) => r.json());
```

From then on, a submission without a token gets `400 CAPTCHA verification required`, and a bad one gets `400 CAPTCHA verification failed`. The honeypot still runs first, so obvious bots are dropped before the endpoint spends a call verifying their token. The [forms API reference](/docs/api-reference/forms) lists the other settings you can change this way.

Three things to know before you rely on it:

- **One provider per form.** The form holds a single secret, and it has to come from the same provider as the widget on the page. A Turnstile token checked against a reCAPTCHA secret fails.
- **reCAPTCHA v3 scores are enforced at 0.5.** [Google's v3 docs](https://developers.google.com/recaptcha/docs/v3) describe the score as running from 0.0 (very likely a bot) to 1.0 and leave the threshold to you (November 2026). OSForms rejects v3 tokens that score below 0.5. That cutoff is fixed, not a per-form setting. v2 tokens carry no score, so they're simply valid or not.
- **Verification fails closed.** If the provider doesn't answer within 5 seconds, the submission gets `400 CAPTCHA verification failed` rather than slipping through unchecked.

## Rate Limits: The Layer Under Everything

Every form also has a rate limit, whether you configure it or not: **10 submissions per minute per IP per form** by default. The eleventh request inside the window gets a `429` with a `Retry-After` header giving the seconds left. The limit runs before the honeypot check, so a bot hammering your form gets throttled even when its submissions would be thrown away anyway.

Ten a minute is generous for a contact form. Nobody sends three messages a minute by hand. You can lower it with the same API call as above, anywhere from 1 to 1000:

```js
body: JSON.stringify({ rateLimit: 3 }),
```

Know what this layer is. The counter is kept in memory on each server instance, keyed on the client IP, in a fixed 60-second window. On a serverless host, concurrent instances each keep their own count, and a botnet spread across many IPs never hits any single limit. Treat it as a brake on bursts, not a wall.

Here's how the layers stack up:

| Layer          | Catches                                 | Misses                                 | Cost to real visitors  |
| -------------- | --------------------------------------- | -------------------------------------- | ---------------------- |
| Honeypot field | Bots that fill every input              | Targeted scripts, browser bots, humans | None                   |
| Rate limit     | Bursts from one IP                      | Slow or distributed spam               | None                   |
| CAPTCHA        | Most automation, including browser bots | Human spam, CAPTCHA-solving services   | A challenge, sometimes |
| Moderation     | Everything                              | Nothing, but it's your time            | None                   |

## A Honeypot Field Is the Cheapest Layer

Start with a honeypot field and the default rate limit. For a portfolio, a docs site, or a small business contact form, that pair handles the drive-by spam that makes up most of what arrives, and your visitors never see a puzzle. Add reCAPTCHA when the spam that gets through is worth the friction, not before.

> The best spam filter is one your visitors never notice. Make the bot do the work, and give it a success page for its trouble.
